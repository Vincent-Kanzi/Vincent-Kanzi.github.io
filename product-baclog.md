# 03. Product Backlog
## OPA Portal Redevelopment

The Product Backlog contains the functional requirements,
improvements and development activities identified for the OPA
Portal redevelopment.

Items are prioritised using the MoSCoW prioritisation technique
to help identify which requirements are essential and which can
be considered for future development.

---

## 1. MoSCoW Prioritisation

| Priority | Meaning |
|---|---|
| Must Have (M) | Essential requirements for the system or agreed release. |
| Should Have (S) | Important requirements that improve the system. |
| Could Have (C) | Useful improvements that can be considered if time allows. |
| Won't Have (W) | Not included in the current scope or release. |

## 3. Backlog Refinement

The Product Backlog should be reviewed regularly as the project
progresses.

During backlog refinement, the team should:

- Clarify the requirements of each backlog item.
- Identify dependencies between features.
- Break large requirements into smaller development tasks.
- Estimate the effort required for implementation.
- Reconsider priorities when project requirements change.
- Remove or revise items that are no longer relevant.

## 4. Prioritisation Rationale

Request submission and approval functionality is prioritised
because it supports the core purpose of the OPA Portal.

The unified Requests workflow is important because it provides
a central point for managing different staff service requests.

Notifications are also important because staff members need
information about the progress and outcomes of their submissions.

Dashboard and interface improvements support usability and make
the portal easier to navigate.

Quality assurance is considered throughout the development
process because changes to an existing application can affect
other system functionality.

## 5. Backlog Maintenance

The Product Backlog is a working document rather than a fixed list.
New requirements, defects and improvements may be added as the
team receives feedback and gains a better understanding of the
system.

Backlog items should be updated to reflect their actual priority,
estimated effort and implementation status.

## 6. Reflection

Developing a Product Backlog helps organise project requirements
and provides a shared view of the work that needs to be considered.

The MoSCoW method is useful because not every improvement has
the same level of importance. Core request functionality and
approval processes need to be considered alongside interface
enhancements and supporting features.

The backlog also makes it easier to identify dependencies,
plan future work and adapt to changing requirements during
the redevelopment process.
